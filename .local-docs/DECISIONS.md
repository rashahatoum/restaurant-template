## 2026-11-12 — D7c: the dashboard menu area saves to the Laravel API — Proposed (approved by the backend developer; owner review in the PR)
- **Server data and the draft, merged:** with the API on, `getDashboardSeed()` reads `GET /admin/categories` + `GET /admin/products` (token, not cached) and sets `menuSource: "api"`; the rest stays mock. `useDashboardData` / `currentData()` show the draft as before, but **categories and products always come from the latest server seed** (`withServerMenu`), never from an older draft. `registerSeed` now keeps the latest seed, not the first. The menu screens don't change. (Rejected: a separate data hook per screen, a rewrite of every menu screen.)
- **Repository router:** `repository`'s 10 menu methods go to `apiMenuRepository` when the seed says `menuSource: "api"` (the client can't read `API_BASE_URL`), else to `localRepository`; every other method stays local.
- **Server Actions** (`dashboard/menu-actions`): one per method, inputs checked before they reach a URL (slug as one encoded segment, direction `up`/`down`), the user's token on every call (Laravel enforces it). After a save: `updateTag("menu")` (read-your-own-writes: the owner checks the public site right after) + `refresh()` (the dashboard page re-renders with fresh admin data in the same round trip).
- **Photos routed by area:** `ImagePicker area="menu"` (products, category cards) uploads to `POST /admin/uploads`; offers, banners and About keep theirs in IndexedDB, because the API deletes an upload no API record uses after 24 h.
- **Failures:** a `401` from any menu call → `/dashboard/session-expired?next=<page>` (an unsaved form is lost; only after a revoked/expired token); the seed's own `401` → the same route. A Server Action call that fails (no connection, body too large) becomes a `Result` (`offline` / `server`), never a thrown error, so no screen is stuck loading.
- **New sizes:** sent with `id: ""` (local `new-…` key for React only); the draft gives them an id like the API does. Only the **save** payload empties the id: the form's live preview keeps the local keys (`sizeGroup(…, "preview")`), or two new sizes would both be key `""` (React's duplicate-key warning, found by the backend developer in `next dev`).
- **Body limit 4 MB** (`serverActions.bodySizeLimit`): Safari can't encode WebP, so iPhone cut-outs upload as PNG and can pass 1 MB; Vercel functions refuse bodies over 4.5 MB.
- **Honest UI:** with the API on, the dashboard notice says the categories and products are saved on the server and reach customers, the rest is still a trial on this device; «رجّع البيانات الأصلية» says it doesn't touch the menu. Default `conflict` text made generic (API-CONTRACT §5).
- **Verified:** lint, typecheck, build with the API on and off. Mock mode in headless Edge (throwaway env-var account): login, a size added and saved (existing ids kept, the new one got `size-…`, no `new-` or empty id saved), dashboard pages render with no client errors, trial notice unchanged. API-mode writes, by the backend developer with the demo's test account (`next dev`): live notice; category create / rename / move / delete; delete refused with the API's 409; photos on a category card and a product; full product save with a new size (no 422); quick price change + undo; best-seller move and remove + undo back in place; the public `/menu` showed each change right away; test items deleted afterwards.

## 2026-11-12 — D7a: login through the Laravel API — Accepted (merged in PR #44)
- **One client:** `lib/api/client.apiFetch()` (server only) is the only caller of the API: base URL, `Accept` / `Accept-Language: ar` / `X-Frontend-Key` on every call, the Bearer token read from the session, `X-Client-IP` on login, 10 s timeout, every failure → `AppError`. Switch: `lib/api/config.isApiEnabled()` (`API_BASE_URL` set). Unset = exactly today (env-var account, mock data, browser draft).
- **Cookie: the same signed cookie, plus the token** (`{ name, exp, token }`), not encrypted. It's `httpOnly` (scripts never read it), `secure`, path `/dashboard`; signing stops edits, and with the key switch on the token alone can't call Laravel. The proxy's check keeps working with no new code. Encrypting (AES-GCM) stays an option if the cookie value ever risks leaking (logs, screenshots).
- **Session trusted until the cookie expires** (7 days, same as the token): no `GET /auth/me` per page (a round trip to Frankfurt, and layouts don't re-render on navigation anyway). With the API on, a cookie without a token (an old env-var login) counts as signed out.
- **`401` → `/dashboard/session-expired`:** a Route Handler that deletes the cookie on its redirect to the login. Needed because a page can't delete cookies, and with a still-valid cookie the proxy would bounce the login page back to the dashboard (endless loop after a revoked token). The proxy lets that path through; `safeDashboardPath` never returns to it; `SessionExpiredDialog` uses a plain `<a>` (a `<Link>` could prefetch the route and sign out before a click).
- **The API not reachable → `server`** «ما قدرنا نوصل للسيرفر، جرّب كمان شوي», not `offline`: the owner's internet works (her action reached Vercel); the Vercel → Hostinger call failed.
- **Logout** calls `POST /auth/logout` first, then deletes the cookie even if the API can't be reached.
- **Verified** (production build, headless Edge, against the demo server): wrong login → the API's «اسم المستخدم أو كلمة السر غلط»; wrong `FRONTEND_API_KEY` → «ما عندك صلاحية» (proves the call reaches Laravel); unreachable API → the `server` text; proxy redirects, forged cookie refused, `session-expired` clears the cookie and never returns to itself; public pages 200. Mock-mode and API-mode builds pass.

## 2026-11-11 — Contract amendments from the backend build — Accepted (merged in PR #39)
What Laravel Phases 1, 3 and 4 (database, auth, menu + uploads) settled while building; API-CONTRACT is amended to match. No frontend code changes now; the tasks are in API-CONTRACT §7.
- **Slugs: optional `slug` in the bodies, neutral id when empty** (`cat-` / `item-` / `offer-` / `branch-xxxxxxxx`; kept on update). Supersedes "suggested from the Arabic name" in the entry below: transliteration on the real menu gave `shaorma-gag` and `frog`.
- **Sizes, phones, banners and reviews get database ids** (`"12"`); mock ids don't survive seeding. Slugged records keep their ids, so URLs and QR codes don't change.
- **`PUT` = whole record, `PATCH` = partial.** The forms drop `undefined` keys when serializing, so a whole-record save must treat a missing field as cleared; a quick change must leave it alone. Products now (`saveProduct` → `PUT`, `updateProduct` → `PATCH`), offers / banners / reviews later.
- **Creates answer `201`.** Standard REST; the body is still the saved record.
- **Image fields accept only our own upload URLs** («الصورة مش من الصور المرفوعة، ارفعها من جديد»): no links to other hosts, and the daily cleanup knows which files are used. Uploads checked by content, ≤ 4000 px, never SVG (it can carry scripts).
- **Login limit per browser:** `X-Client-IP` + `X-Frontend-Key` (secret `FRONTEND_API_KEY`), because every dashboard login reaches the API from Vercel's IP. Only failed tries count. Logout must call `POST /auth/logout`, or the token stays valid 7 days. Admin account via `php artisan admin:create`; a password change logs out every device.
- **Category `PATCH`** takes `name?`, `slug?`, `image?` (one endpoint for rename and photo); Arabic texts for duplicate name and the `409` on delete copied from the dashboard.
- **Products:** `PATCH` accepts `bestSellerOrder` (the undo's fractional place, renumbered 1…n); `POST` accepts it, `PUT` keeps the current place. New rule: a quick price change can't make a size cost ≤ 0. The size group is always `id: "size"`, required, one choice.
- **Nested ids that don't belong to the parent are refused** (`422`, «هالحجم مش تابع لهالصنف، حدّث الصفحة»), so a stale tab can't move another product's size; phones and branches will follow.
- **Gone references come back as `""`** in admin GETs (banner target, delivery phone), so the dashboard shows "target gone". `GET /admin/ordering` lists every branch, as `toOrderingFormValues` already merges.

## 2026-11-11 — API contract agreed with the backend developer — Accepted (owner + backend developer)
- **Separate repo for Laravel**, not a folder here: no code is shared across the HTTP line, the two deploy to different hosts, and this repo's rules keep backend code out. The contract docs stay here (`API-CONTRACT.md` is the agreed version; changes by PR). Working rules: BACKEND_REQUIREMENTS §11.

- **Conventions:** Sanctum Bearer tokens valid 7 days (login limited to 5 tries a minute); camelCase JSON matching `src/types/`, not wrapped in `data`, empty optional fields left out; ids always strings, slugs as the public ids of categories, products, offers and branches; Arabic messages always (API-CONTRACT §2).
- **Slugs:** suggested by the backend from the Arabic name, **editable by the owner** (a «رابط الصفحة» field, planned in the forms), never changed by themselves. Today's browser draft still gives new items random ids (`lib/dashboard/ids`); Laravel replaces that.
- **`move` instead of `reorder`:** `POST …/{id}/move { direction }` returns the list in order, matching the repository's `moveX(id, direction)`; one transaction, no stale full list sent from an old tab (API-CONTRACT §4.2).
- **Lists saved by id:** sizes, phones and branches are updated row by row and never recreated, because cart lines keep the size's `optionId`, ordering keeps `phoneId`, and QR codes keep branch ids (API-CONTRACT §4.1).
- **`409` = a business rule** (always with an Arabic message). No edit-conflict detection with one admin, so the default `conflict` text in `lib/api/errors.ts` becomes generic (frontend task when the API is connected). Image too large: `422` on `image` (over 5 MB) or a bare `413` (over PHP's limit).
- Frontend work this implies is listed in API-CONTRACT §7; nothing changes in the code until an area switches to the API.

- **Why:** functions can't be passed from a Server Component to a Client Component, but server-rendered elements can, so cards stay server-rendered and only the slider ships JS. Plain props keep the card usable for any data source.
- **Motion:** slides share one grid cell and move with CSS transitions by their offset from the active slide; a slide that wraps around (last ↔ first) fades in instead of sliding across. No library.
